### [A2A 协议有哪五大设计原则？](https://www.mianshiya.com/bank/1906189461556076546/question/1916425043148128258)

> **答案**：
>
> **A2A（Agent2Agent Protocol）由 Google 于 2025 年发布，是开放协议，目标是让不同厂商、不同框架构建的 Agent 能跨组织、跨网络协作**。
>
> 五大核心设计原则：
>
> **1. Embrace agentic capabilities（拥抱 Agent 多步推理能力）**
> 不要把对方 Agent 当成简单的 RPC 服务调用。Agent 内部可能有复杂的多步推理、状态机、长任务。A2A 让调用方知道"我面对的是一个能自主决策的 Agent，不是无状态函数"——支持长任务、流式增量结果、可中断、可追问。
>
> **2. Build on existing standards（建立在现有 Web 标准之上）**
> 不重新发明轮子。A2A 用 **HTTP + JSON-RPC 2.0** 作为传输层，复用现有认证（OAuth2、Bearer Token）、加密（HTTPS）、网关基础设施。这意味着企业无需改造现有 IT 就能部署。
>
> **3. Secure by default（默认安全）**
> 所有交互默认走 HTTPS；Agent 之间需要双向认证；权限粒度细到单个 Task；强调"不信任对方"的零信任模型——你以为你在调用同事的 Agent，可能是被诱导调用攻击者 Agent。
>
> **4. Support long-running tasks（支持长任务）**
> 真实 Agent 任务往往耗时几分钟到几小时（深度研究、代码审计、批处理）。A2A 不假设"请求-响应"模型，而是：
> - 提交任务 → 拿到 task_id
> - 轮询或 SSE 流式获取进度
> - 任务可取消、可更新输入
> - 任务结束拿最终结果
>
> **5. Modality agnostic（模态中性）**
> Agent 输入输出不只是文本——可能含图像、音频、视频、结构化数据、文件。A2A 用 **Artifact** 抽象承载多模态产物（带 mime type），不绑定单一模态。
>
> **总结**：A2A 把"两个 Agent 协作"这件复杂事拆成 5 个工程原则——**承认 Agent 复杂、复用 Web 基础、默认安全、支持长任务、模态中立**。这五个原则共同决定了 A2A 协议的形态（JSON-RPC over HTTP + Task lifecycle + Artifact + Agent Card）。
>
> 参考：[Google A2A 协议官方仓库 github.com/google/A2A](https://github.com/google/A2A) 与规范文档。

### [A2A 协议的工作原理是怎样的？](https://www.mianshiya.com/bank/1906189461556076546/question/1916425043395592193)

> **答案**：
>
> A2A 协议的工作原理可以分成三层理解：**发现层、通信层、任务层**。
>
> **1. 发现层：Agent Card（数字名片）**
>
> 每个 A2A 兼容 Agent 在固定路径 `/.well-known/agent.json` 暴露一张 **Agent Card**（JSON 文档），描述：
> ```json
> {
>   "name": "CodeReviewer",
>   "description": "Reviews pull requests for security and style",
>   "version": "1.0.0",
>   "capabilities": {
>     "streaming": true,
>     "push_notifications": true
>   },
>   "skills": [
>     {"id": "security_review", "name": "Security Review", ...},
>     {"id": "style_review", "name": "Style Review", ...}
>   ],
>   "authentication": {"schemes": ["bearer"]},
>   "endpoints": {"rpc": "https://...", "stream": "wss://..."}
> }
> ```
>
> 调用方先 GET 这张卡，知道对方能做什么、怎么认证、怎么通信。
>
> **2. 通信层：JSON-RPC 2.0 over HTTP(S)**
>
> 所有交互是标准 JSON-RPC：
> - `tasks/send` — 提交或追加消息到任务
> - `tasks/get` — 查询任务状态与产物
> - `tasks/sendSubscribe` — 提交 + SSE 流式订阅
> - `tasks/cancel` — 取消任务
> - `tasks/pushNotification/set` — 注册服务端推送回调
>
> 流式场景用 SSE（Server-Sent Events），不重新发明传输。
>
> **3. 任务层：Task Lifecycle**
>
> 任务有清晰状态机：
> ```
> submitted → working → input-required (需用户补充)
>                    ↘ completed
>                    ↘ failed
>                    ↘ canceled
> ```
>
> 任务有：
> - **Message**（用户或 Agent 发的消息，含 Parts：text / file / data）
> - **Artifact**（任务产物，如生成的报告、代码、图片）
> - **History**（消息历史）
>
> **完整工作流举例**（Agent A 让 Agent B 审查代码）：
>
> 1. **A 发现 B**：GET `https://B/.well-known/agent.json` 拿到 B 的 Agent Card
> 2. **A 提交任务**：POST 到 B 的 RPC 端点，方法 `tasks/send`：
>    ```json
>    {"task_id": "t-001", "message": {"role":"user", "parts":[{"text":"review PR #42"}]}}
>    ```
> 3. **B 返回 working 状态** + 异步处理
> 4. **A 流式订阅**（或轮询）：通过 SSE 接收 B 的中间进度（"正在解析 diff..."、"发现 3 个问题..."）
> 5. **B 需要补充信息**：状态变 `input-required`，A 追加输入
> 6. **B 完成**：状态 `completed`，附 Artifact（评审报告）
> 7. **A 取回 Artifact**
>
> **关键设计点**：
> - **Agent 是有状态的**（不是 RPC）：A 不该假设 B 立即返回，要支持长任务
> - **Artifact 与 Message 分离**：Message 是过程，Artifact 是产物
> - **认证在传输层**：HTTPS + Bearer Token，不重新造安全模型
> - **跨厂商**：A 用 LangChain，B 用 AutoGen，只要都遵守 A2A 就能互通

### [A2A 协议的工作流程是怎样的？](https://www.mianshiya.com/bank/1906189461556076546/question/1916425043643056130)

> **答案**：
>
> A2A 工作流程从"调用方想用某个 Agent"到"拿到结果"完整链路如下：
>
> **阶段 1：发现 Agent Card**
> ```
> Client → GET https://agent-b.example.com/.well-known/agent.json
>        ← 200 OK, Agent Card JSON
> ```
> 调用方读 Card，了解：
> - Agent 名称、版本、能力描述
> - 支持的 skills（任务类型）
> - 端点 URL（RPC、流式）
> - 认证方式
>
> **阶段 2：认证授权**
> 按 Card 中声明的 `authentication.schemes` 准备凭证。主流：
> - OAuth2（企业级，token 来自 IdP）
> - Bearer Token（API Key 风格）
> - 双向 TLS（高安全）
>
> **阶段 3：创建任务**
> ```
> Client → POST {rpc_endpoint}
>          JSON-RPC method: "tasks/send"
>          params: {
>            "task_id": "uuid-...",
>            "session_id": "...",  // 可选，跨任务关联
>            "message": {
>              "role": "user",
>              "parts": [
>                {"text": "Analyze Q3 sales data and report trends"},
>                {"file": {"mimeType":"text/csv", "data":"<base64>"}}
>              ]
>            }
>          }
> ```
>
> 服务端响应：
> ```json
> {
>   "task_id": "uuid-...",
>   "status": {"state": "submitted"},
>   "config": {"blocking": false}  // 是否阻塞等待
> }
> ```
>
> **阶段 4：执行与进度同步**
>
> 三种模式：
> - **同步阻塞**：任务快时，rpc 调用直接返回 completed 状态 + Artifact
> - **轮询**：调用方周期性 `tasks/get` 查状态
> - **流式订阅（推荐）**：用 `tasks/sendSubscribe` 走 SSE，实时接收状态变更和中间消息
> - **服务端推送**：注册 webhook，服务端在状态变化时主动推送给调用方指定的 URL
>
> 任务状态机：`submitted → working → (input-required) → completed / failed / canceled`
>
> **阶段 5：多轮交互（如有）**
>
> 如果 Agent 需要追问用户：
> ```
> status: input-required
> message: {"role":"agent", "parts":[{"text":"需要哪个月份的明细？"}]}
> ```
> 调用方追加消息再次 `tasks/send`，任务继续。
>
> **阶段 6：取回 Artifact**
>
> 任务完成后返回的 Artifact 是结构化产物：
> ```json
> {
>   "task_id": "uuid-...",
>   "status": {"state":"completed"},
>   "artifacts": [
>     {
>       "artifact_id": "report-1",
>       "name": "Q3 Sales Report",
>       "parts": [
>         {"text": "Q3 sales grew 12% YoY..."},
>         {"file": {"mimeType":"application/pdf", "data":"..."}}
>       ]
>     }
>   ]
> }
> ```
>
> **阶段 7：取消与超时**
>
> 调用方主动取消：`tasks/cancel`。服务端清理资源，状态变 `canceled`。超时由双方约定，A2A 不强制。
>
> **与 MCP 的协作**：
> A2A 解决 Agent↔Agent，MCP 解决 Agent↔Tool。一个 A2A 远程 Agent 内部可能用 MCP 接入自己的工具——两者层次不同，互补不冲突。

### [什么是 A2A 协议，它的核心架构及主要组件有哪些？](https://www.mianshiya.com/bank/1906189461556076546/question/1916425042913247233)

> **答案**：
>
> **A2A（Agent2Agent Protocol）是 Google 于 2025 年发布的开放协议，目标是让不同框架、不同厂商构建的 AI Agent 能跨网络协作**。它解决"我用 LangChain 做的 Agent，怎么调用你用 AutoGen 做的 Agent"这一互操作问题。
>
> **核心架构**：
>
> ```
> +-------------------+                    +-------------------+
> |   Agent A (Client)|  ----- HTTP ---->  |   Agent B (Server)|
> |                   |  JSON-RPC 2.0      |                   |
> |   - has tasks     |  <---- SSE ------  |   - exposes skills|
> |   - discovers     |                    |   - runs tasks    |
> |     Agent Cards   |                    |   - returns       |
> |                   |                    |     artifacts     |
> +-------------------+                    +-------------------+
> ```
>
> A2A 是 **client-server 架构**：发起方 Agent 是 client，被调用方 Agent 是 server。但角色可以反转——同一 Agent 既可当 client 也可当 server。
>
> **主要组件**：
>
> **1. Agent Card（数字名片）**
> - 每个兼容 Agent 在 `/.well-known/agent.json` 暴露能力描述
> - 含：name、description、version、capabilities、skills、authentication、endpoints
> - 让调用方知道"这个 Agent 能做什么、怎么调"
>
> **2. Task（任务）**
> - A2A 协作的核心单位
> - 有唯一 task_id、状态机（submitted/working/input-required/completed/failed/canceled）
> - 支持长任务（小时级）、可取消、可追加输入
> - 关联 message 历史和 artifact 产物
>
> **3. Message（消息）**
> - 任务内的对话单元
> - 含 role（user/agent）和 parts（多模态内容）
> - 是过程性信息（提问、回复、追问）
>
> **4. Artifact（产物）**
> - 任务的最终输出
> - 与 Message 区分：Artifact 是产物，Message 是过程
> - 含 name、description、parts（多模态）
> - 例如：分析报告、生成的代码、图片、数据集
>
> **5. Part（消息/产物的内容单元）**
> - 多模态内容的最小单位
> - 类型：TextPart、FilePart、DataPart
> - 一条 Message 可含多个 Part（如文本 + 图片 + 结构化数据）
>
> **6. Skill（能力声明）**
> - Agent Card 中声明 Agent 擅长的具体任务类型
> - 帮助调用方判断该 Agent 是否合适
> - 每个 skill 有 id、name、description、可选 tags
>
> **7. RPC 方法集（协议端点）**
> - `tasks/send`：提交/追加任务消息
> - `tasks/get`：查询任务状态
> - `tasks/sendSubscribe`：提交 + 流式订阅
> - `tasks/cancel`：取消任务
> - `tasks/pushNotification/set`：注册推送回调
>
> **与 MCP 的关系**：A2A 管 Agent↔Agent，MCP 管 Agent↔Tool。同一 Agent 通常**对外用 A2A 接受任务，对内用 MCP 调用工具**——两者层次互补。
>
> **核心价值**：把 Agent 从孤岛变成互联网节点。理论上未来 Agent 可以像 Web 一样互联——你的日历 Agent 调用航空公司 Agent 改签，调用酒店 Agent 取消预订，调用报销 Agent 发起退款，全程自动。

### [A2A 协议中的 Agent Card 是什么？它在多 Agent 发现和协作中起什么作用？](https://www.mianshiya.com/bank/1906189461556076546/question/2052284761493221377)

> **答案**：
>
> **Agent Card 是 A2A 协议中每个 Agent 的"数字名片"——一个标准化的 JSON 文档，让任何潜在调用方知道这个 Agent 是谁、能做什么、怎么调用**。
>
> **作用**：
>
> 1. **发现**：让其他 Agent 能找到你、了解你的能力
> 2. **能力声明**：明确你能处理什么任务、不能处理什么
> 3. **契约**：声明端点、认证、限流，让调用方知道怎么对接
> 4. **版本管理**：版本号让调用方判断兼容性
>
> **位置**：每个 A2A 兼容 Agent 必须在 `https://<agent-host>/.well-known/agent.json` 暴露 Card。这是约定俗成的发现路径，类似 robots.txt 或 OpenID Connect 的 discovery。
>
> **结构（典型字段）**：
>
> ```json
> {
>   "name": "TravelBookingAgent",
>   "description": "Books flights and hotels, handles changes and cancellations",
>   "version": "2.1.0",
>   "protocol_version": "0.3",
>   "url": "https://travel.example.com",
>   "endpoints": {
>     "rpc": "https://travel.example.com/rpc",
>     "stream": "https://travel.example.com/stream"
>   },
>   "capabilities": {
>     "streaming": true,
>     "push_notifications": true,
>     "state_transition_history": true
>   },
>   "skills": [
>     {
>       "id": "book_flight",
>       "name": "Book Flight",
>       "description": "Search and book flights by route and date",
>       "tags": ["travel", "flight"],
>       "input_modes": ["text", "file"],
>       "output_modes": ["text", "file"]
>     },
>     {
>       "id": "cancel_reservation",
>       ...
>     }
>   ],
>   "default_input_modes": ["text", "voice"],
>   "default_output_modes": ["text"],
>   "authentication": {
>     "schemes": ["bearer", "oauth2"]
>   },
>   "documentation_url": "https://travel.example.com/docs",
>   "icon_url": "https://travel.example.com/icon.png"
> }
> ```
>
> **在多 Agent 发现和协作中起的作用**：
>
> **1. 服务发现（核心）**
> Agent 想找"会订机票"的合作方 → 扫描已知 Agent 列表 / 注册中心 → 拉取每张 Card → 根据 skills 匹配 → 选定目标。
>
> **2. 能力路由**
> 多 Agent 系统中，路由器收到用户请求后，按请求类型匹配 Agent Card 的 skills，把任务路由给最合适的 Agent。
>
> **3. 自动化对接**
> 开发者拿到 Agent Card 后，可以用工具自动生成 client SDK（类似 OpenAPI Codegen），不需要手写集成代码。
>
> **4. 安全审计**
> 管理员审查 Agent Card 列表，发现"这个 Agent 声明能调金融 API，合理吗？"——Card 是审计入口。
>
> **5. 协作图谱**
> 多个 Agent 的 Card 关联起来（Card A 调用 Card B），形成可观测的协作拓扑，便于排障和监控。
>
> **与 MCP 工具发现的关系**：
> - MCP 的 `tools/list` 是 Agent 内部工具发现（一个 Agent 暴露自己有什么工具）
> - A2A Agent Card 是网络层 Agent 发现（一个 Agent 暴露自己是什么 Agent）
>
> 两者层次不同：先通过 Agent Card 找到目标 Agent，调用任务时该 Agent 内部再用 MCP 调自己的工具。
